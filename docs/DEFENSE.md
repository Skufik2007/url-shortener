# Шпаргалка к защите курсовой (вариант 29)

**Тема:** «Сервис сокращения ссылок с аналитикой» (аналог bit.ly).
**Стек по варианту:** Go + PostgreSQL + Redis.

---

## 1. О проекте за 30 секунд (начало доклада)

> Я разработал сервис, который превращает длинную ссылку в короткую вида `site/abc1234`.
> При переходе по короткой ссылке сервис перенаправляет пользователя на исходный адрес
> и записывает статистику: сколько было переходов, из каких стран, с каких сайтов пришли
> посетители, с каких браузеров и устройств. Владелец ссылок видит всё это в личном кабинете
> (дашборде). Бэкенд написан на Go, данные хранятся в PostgreSQL, популярные ссылки
> кэшируются в Redis, чтобы редирект был максимально быстрым. Проект упакован в Docker,
> покрыт тестами и проверяется в CI на GitHub Actions.

---

## 2. Как устроено — простыми словами

Приложение — **один Go-процесс** из нескольких слоёв. Каждый слой знает только о слое ниже,
причём через **интерфейсы**, а не конкретные реализации. Благодаря этому базу или кэш можно
подменить: в тестах и в демо-режиме вместо PostgreSQL и Redis работают реализации в памяти (в демо-режиме их можно сохранять в файл `data.json`, см. раздел 15).

| Слой | Пакет | Что делает |
|---|---|---|
| Транспорт | `internal/httpapi` | Принимает HTTP-запросы, проверяет токен, ограничивает частоту, отдаёт JSON и редиректы |
| Бизнес-логика | `internal/service` | Правила: какой URL допустим, как генерировать код, когда класть ссылку в кэш |
| Хранилище | `internal/storage/postgres`, `memory` | Ссылки, пользователи, переходы |
| Кэш | `internal/cache` (Redis / память) | Популярные ссылки и счётчики обращений |
| Аналитика | `internal/analytics` | Асинхронный сбор переходов: очередь (канал) + воркеры (горутины) |
| Авторизация | `internal/auth` | Регистрация, вход, bcrypt, подписанные токены |
| Дашборд | `web/static` | HTML + JS без фреймворков; встроен прямо в бинарник через `embed` |
| Точка входа | `cmd/shortener/main.go` | Собирает всё вместе, корректно завершает работу по Ctrl+C |

**Главная идея архитектуры:** редирект должен быть быстрым, поэтому запись статистики
**не задерживает** ответ пользователю. Обработчик кладёт событие в очередь и сразу отвечает
`302`, а запись в БД выполняется в фоне пачками.

## 3. Что происходит при переходе по ссылке (самый частый вопрос!)

1. Браузер запрашивает `GET /abc1234`.
2. Сервис быстро проверяет формат кода (только `A-Z a-z 0-9 _ -`, до 32 символов); мусор сразу получает 404, в базу запрос не идёт.
3. Ищет код в **Redis**. Если нашёл (cache hit), обращения к БД нет вообще.
4. Если не нашёл (cache miss), берёт ссылку из **PostgreSQL** и проверяет, что она активна и не истекла.
5. Увеличивает в Redis счётчик обращений к этому коду (`INCR`). Если за **10 минут** было **≥ 3** обращений, ссылка считается популярной и кладётся в кэш на **1 час** (но не дольше срока жизни ссылки).
6. Кладёт событие перехода (IP, User-Agent, Referer, время) в **буферизованный канал** без ожидания.
7. Отвечает `302 Found` + `Location: <исходный адрес>` + `Cache-Control: private, max-age=0`.
8. В фоне 4 воркера-горутины берут события из канала, определяют страну, браузер, ОС, устройство и домен источника, а затем пачками (до 500 штук или раз в секунду) пишут в PostgreSQL через `COPY`.

**Почему 302, а не 301?** Ответ 301 браузер кэширует навсегда, и повторные переходы до сервера не дойдут: статистика будет неполной, а отключить ссылку станет невозможно. Ответ 302 с запретом кэширования гарантирует, что каждый переход учитывается.

**Почему кэшируются не все ссылки?** Большинство ссылок открывают пару раз, и держать их в памяти невыгодно. Порог популярности позволяет кэшировать только «горячие» ссылки.

**Что если Redis упал?** Сервис продолжит работать: ошибки кэша логируются, а данные читаются напрямую из PostgreSQL (graceful degradation). Это проверено тестом.

**Что если очередь аналитики переполнилась?** Событие отбрасывается, а счётчик `dropped` растёт (виден в `/metrics`). Пользователь при этом всё равно получает редирект: скорость важнее статистики.

## 4. Создание ссылки

1. Пользователь вошёл и получил токен; токен передаётся в заголовке `Authorization: Bearer ...`.
2. `POST /api/v1/links` с телом `{url, alias?, title?, expires_at?}`.
3. Проверки: только `http`/`https`, длина ≤ 2048, нельзя сокращать ссылку на сам сервис (иначе получились бы цепочки редиректов), срок жизни — в будущем.
4. Если задан свой алиас, он проверяется (3–32 символа, не зарезервированное слово вроде `api` или `dashboard`); если занят — ответ `409`.
5. Иначе генерируется случайный код из 7 символов base62 криптостойким генератором `crypto/rand`. При совпадении с существующим (коллизии) делается до 5 попыток.

**Почему случайный код, а не счётчик?** Счётчик (1, 2, 3…) позволяет перебрать все ссылки, в том числе «приватные». Случайный код угадать нельзя.

**Сколько всего кодов?** 62⁷ ≈ 3,5 триллиона. Даже при 10 миллионах ссылок шанс коллизии на одну вставку — около 0,0003 %, а на этот случай есть повтор.

**Что такое rejection sampling?** Байт даёт 256 значений, а символов 62; 256 не делится на 62, поэтому `байт % 62` чаще выдавал бы первые символы. Байты ≥ 248 (4·62) отбрасываются, и распределение становится строго равномерным.

## 5. Аналитика: откуда берутся данные

| Показатель | Откуда | Как обрабатывается |
|---|---|---|
| Источник (реферер) | заголовок `Referer` | хранится только домен (`t.me`, `google.com`); пусто → `direct` |
| Браузер, ОС, устройство | заголовок `User-Agent` | собственный разбор; важен порядок проверок: Edge, Opera и Яндекс содержат слово `Chrome`, а Chrome содержит `Safari`; боты (`curl`, `bot`, `spider`) помечаются как `bot` |
| Страна | заголовок CDN `CF-IPCountry` или база GeoLite2 по IP | заголовку доверяем **только** при `TRUST_PROXY=true`, иначе его можно подделать; неизвестно → `ZZ` |
| Уникальные посетители | хэш SHA-256 от (соль + IP + User-Agent) | **IP в базе не хранится** — это персональные данные (152-ФЗ) |
| Динамика | время перехода | группировка по дням в SQL |

## 6. Безопасность (обязательный пункт методички)

- **Пароли:** хранится только хэш bcrypt (стоимость 12), сам пароль нигде не сохраняется.
- **Токены:** `userID.срок` + подпись HMAC-SHA256; подпись сравнивается за постоянное время (`hmac.Equal`), чтобы её нельзя было подобрать по времени ответа. JWT не использовал: он сложнее и известен уязвимостями вроде `alg=none`, а здесь хватает простой подписи.
- **Вход:** при неверном email выполняется такая же проверка bcrypt, как при неверном пароле, поэтому по времени ответа нельзя узнать, зарегистрирован ли email.
- **Rate limiting:** алгоритм token bucket по IP (5 запросов/с, запас 20) на регистрацию, вход и создание ссылок; превышение → `429`.
- **SQL-инъекции:** все запросы параметризованы (`$1, $2`), конкатенации строк нет.
- **XSS в дашборде:** данные выводятся через `textContent`; заголовок CSP запрещает чужие скрипты.
- **Заголовки:** `X-Content-Type-Options`, `X-Frame-Options: DENY`, `Referrer-Policy`, `Content-Security-Policy`.
- **Open redirect:** сокращатель по своей природе — редиректор, поэтому разрешены только `http`/`https` (никаких `javascript:`), ссылки создают только зарегистрированные пользователи, а ссылки на сам сервис запрещены.
- **Размер запроса** ограничен 64 КБ.
- **SAST/SCA:** `go vet`, `golangci-lint` (с `gosec`), `govulncheck`, dependabot. govulncheck нашёл 13 уязвимостей в стандартной библиотеке Go 1.27.1 (10 из них достижимы из кода). Все исправлены в Go 1.27.2. Версия закреплена строкой `toolchain go1.27.2` в `go.mod`, и Go сам переключается на неё. Повторная проверка показала 0 уязвимостей, достижимых из кода.
- **gosec** проверил 28 файлов (3858 строк) и нашёл 0 проблем. После добавления сохранения в файл он дал два замечания G304 («чтение файла по пути из переменной»); я не заглушил их комментарием `#nosec`, а нормализовал путь через `filepath.Clean`. Интересная деталь для защиты: обычная сборка gosec «молча» не умела анализировать Go 1.27 (старая библиотека x/tools) и показывала ложный ноль. Я это заметил по ошибкам в логе, пересобрал gosec с новой x/tools и получил честный результат. Мораль: «зелёный» результат инструмента тоже надо проверять.
- **Docker:** итоговый образ `distroless` без оболочки и пакетного менеджера, процесс запущен не от root.

## 9. Демонстрация на защите (5 минут)

**Основной вариант — с настоящим PostgreSQL (папка «Сократитель ссылок — для защиты»).** Двойной щелчок по `Запустить.bat`:
1. Запускатель включает **собственный экземпляр PostgreSQL 16** программы. Его каталог данных — `%LOCALAPPDATA%\UrlShortener\pgdata`, порт 5433, свой пользователь `shortener` со случайным паролем. Системный PostgreSQL не затрагивается, права администратора не нужны.
2. При первом запуске скрипт `база\настроить.ps1` сам создаёт кластер (`initdb`) и базу, а программа создаёт таблицы встроенными миграциями.
3. После закрытия программы запускатель выключает PostgreSQL (`pg_ctl stop`).

В первых строках журнала в окне консоли видно «хранилище: PostgreSQL». Это и есть ответ на вопрос «а база настоящая?». Если хотите показать таблицы прямо в базе, откройте psql:

```bash
"C:\Program Files\PostgreSQL\16\bin\psql.exe" -h 127.0.0.1 -p 5433 -U shortener -d shortener
```

Пароль лежит в файле `база\подключение.cmd`. Удобные запросы: `\dt` (список таблиц), `SELECT code, original_url, click_count FROM links;`, `SELECT count(*) FROM clicks;`.

**Почему отдельный экземпляр, а не системный PostgreSQL?** У системного свой администратор и пароль, а программе нужны изолированная база и пользователь с минимумом лишнего. Отдельный кластер на своём порту не мешает другим проектам, его легко удалить (просто папка), и он настраивается без прав администратора Windows.

**Запасной вариант без базы.** Сервис работает с хранилищем в памяти, а при `DATA_FILE` данные ещё и сохраняются в файл (переживают перезапуск; можно показать: закрыть и снова запустить, данные на месте):

```bash
DATA_FILE=data.json go run ./cmd/shortener
```

Откройте `http://localhost:8080/dashboard/` и выполните шаги:
1. Зарегистрируйтесь.
2. Создайте ссылку с алиасом, например `demo`.
3. Откройте `http://localhost:8080/demo` несколько раз (можно из разных браузеров или с телефона в той же сети).
4. Нажмите «Статистика»: появятся переходы, браузеры, устройства и источники.
5. Покажите метрики `http://localhost:8080/metrics` и проверку `http://localhost:8080/healthz`.

**Вариант с Docker (полный стек).** Создайте `.env` с `AUTH_SECRET` (строка из 32 и более символов) и запустите:

```bash
docker compose up --build
```

**Тесты вживую:**

```bash
go test -cover ./...
```

## 11. Вероятные вопросы и ответы

**Почему Go?** Задан вариантом, и он хорошо подходит: встроенная конкурентность (горутины дешевле потоков, каналы для очередей), быстрый HTTP-сервер в стандартной библиотеке, сборка в один статический бинарник (удобно для Docker), высокая производительность при простом синтаксисе.

**Зачем и PostgreSQL, и Redis?** PostgreSQL — основное надёжное хранилище (ACID, связи, агрегатные запросы для статистики). Redis — быстрый кэш в памяти (доли миллисекунды), но данные в нём могут потеряться. Поэтому истина хранится в PostgreSQL, а Redis только ускоряет.

**Что такое горутина и канал?** Горутина — лёгкий поток выполнения Go (несколько КБ памяти, их могут быть сотни тысяч). Канал — типизированная очередь для безопасной передачи данных между горутинами. В проекте обработчик HTTP пишет события в канал, а 4 горутины-воркера читают и сохраняют их.

**Почему пачками, а не по одному?** Одна вставка в БД — это сетевой запрос и транзакция. 500 вставок одной командой `COPY` в десятки раз быстрее, чем 500 отдельных `INSERT`.

**Как корректно останавливается сервис?** По сигналу SIGINT/SIGTERM сервер перестаёт принимать новые запросы и дожидается текущих (`Shutdown`). Затем сборщик аналитики дочитывает очередь и записывает остаток в БД, и только после этого закрываются соединения. Переходы не теряются.

**Как работает токен?** При входе сервер формирует строку `id пользователя + время истечения` и подписывает её секретным ключом (HMAC-SHA256). Клиент присылает токен с каждым запросом, сервер пересчитывает подпись и сравнивает. Подделать токен без секрета нельзя. Срок жизни — 72 часа.

**Почему bcrypt, а не SHA-256 для паролей?** SHA-256 очень быстрый, поэтому перебор паролей тоже быстрый. bcrypt специально медленный (параметр cost) и добавляет соль, что делает перебор и радужные таблицы непрактичными.

**Что такое rate limiting и token bucket?** Ограничение частоты запросов. У каждого IP есть «ведро» на 20 жетонов, которое пополняется со скоростью 5 жетонов в секунду; каждый запрос забирает один жетон. Пустое ведро означает ответ 429 Too Many Requests. Это защищает от перебора паролей и спама ссылками.

**Как считаются уникальные посетители, если IP не хранится?** Хранится только хэш SHA-256 от (секретная соль + IP + User-Agent), обрезанный до 16 символов. Одинаковый посетитель даёт одинаковый хэш, а восстановить из хэша IP нельзя.

**Как определяется страна?** Если сервис стоит за CDN (например, Cloudflare), CDN сам присылает заголовок со страной. Иначе используется бесплатная база MaxMind GeoLite2 (файл `.mmdb`), где по IP находится страна. Без того и другого — `ZZ` (неизвестно).

**Что будет, если два пользователя одновременно попросят один алиас?** В БД на поле `code` стоит ограничение `UNIQUE`, поэтому вторая вставка получит ошибку уникальности (код 23505). Она превращается в ответ `409 Conflict`. Гонки нет: проверку выполняет сама база.

**Какие индексы есть и зачем?** `links(code)` UNIQUE — для поиска при редиректе; `links(owner_id, created_at)` — для списка ссылок владельца; `clicks(link_id, clicked_at)` — для статистики за период.

**Как сервис масштабировать?** Приложение не хранит состояния в памяти: всё лежит в PostgreSQL и Redis. Поэтому можно запустить несколько экземпляров за балансировщиком. Дальше — кластер Redis, реплики PostgreSQL для чтения, а для очень больших объёмов кликов — колоночная БД (ClickHouse) и партиционирование таблицы `clicks` по дате.

**Почему ~5 600 RPS, а не больше?** Генератор нагрузки работал на той же машине и делил с сервером процессор, а каждый запрос синхронно пишется в лог. На отдельном сервере и с асинхронным логированием будет больше. Для курсовой важно, что ошибок нет и задержка растёт линейно с нагрузкой (закон Литтла: задержка ≈ число клиентов / пропускная способность).

**Что такое distroless?** Минимальный образ, в котором есть только наш бинарник и системные сертификаты, без shell и пакетного менеджера. Меньше размер и меньше поверхность атаки.

**Зачем healthcheck в compose?** Приложение стартует только после того, как PostgreSQL и Redis реально готовы принимать соединения (`depends_on: condition: service_healthy`).

**Что проверяет CI?** На каждый push: `go vet`, тесты с race-детектором и покрытием, интеграционные тесты с настоящим PostgreSQL, golangci-lint, gosec, govulncheck и сборка Docker-образа. Все задания зелёные; репозиторий — github.com/Skufik2007/url-shortener (приватный, вкладка Actions). Первый прогон golangci-lint дал 16 замечаний. Все исправлены, кроме правила о неиспользуемых параметрах: его пришлось отключить, потому что `ctx` требуют интерфейсы.

**Что такое миграции?** SQL-скрипты, которые создают и изменяют схему БД. Они встроены в бинарник и применяются при старте по порядку номеров. Применённые записываются в таблицу `schema_migrations`, а advisory-блокировка не даёт двум экземплярам сервиса применить миграцию одновременно.

**Чем отличается ваш проект от bit.ly?** Это self-hosted решение (данные остаются у владельца), с открытым кодом, без лимитов бесплатного тарифа и с обезличиванием данных. Bit.ly умеет больше: свои домены, QR-коды, интеграции. Это пути развития.

**Что бы вы улучшили?** собственные домены, OAuth-вход, ClickHouse для аналитики, графики в Grafana по метрикам Prometheus, CAPTCHA при регистрации.

## 14. QR-коды и демонстрация с телефона

### Как это работает (простыми словами)

В дашборде у каждой ссылки есть кнопка «QR». Она открывает окно с картинкой: если навести на неё камеру телефона, откроется короткая ссылка. Картинку отдаёт адрес `GET /qr/{код}.png?size=256` (размер от 64 до 1024 пикселей). Что внутри:

1. Обработчик `handleQR` проверяет `size` и вызывает `CheckActive`: ссылка должна существовать, быть включённой и не истёкшей (иначе 404 или 410).
2. Пакет `internal/qrcode` кодирует текст `BASE_URL + "/" + код` в матрицу чёрно-белых квадратиков («модулей»). Саму математику (коды Рида — Соломона, маски) делает библиотека `rsc.io/qr`.
3. Рисует картинку наш код: каждый модуль — квадрат из целого числа пикселей, вокруг белая рамка, результат сохраняется в PNG на 1 бит на пиксель (только чёрный и белый).
4. Ответ кэшируется браузером на час (`Cache-Control: public, max-age=3600`).

### История про два бага библиотеки (хорошо звучит на защите)

Сначала я хотел взять готовые методы библиотеки, чтобы получить PNG. Я написал тест, который генерирует картинку и расшифровывает её **независимым декодером** (gozxing — это Go-порт известной библиотеки ZXing от Google; он подключён только в тестах). Тест на размеры сразу упал: встроенный `Code.PNG()` паникует с ошибкой «invalid flate repeat», если модуль равен одному пикселю (то есть для маленьких картинок). Я полез в исходники библиотеки за другим способом получить картинку и нашёл второй дефект: метод `Code.Image()` игнорирует масштаб и рамку. Размер картинки он отдаёт правильный, но сам код рисует крошечным в левом верхнем углу. Поэтому от библиотеки я использую только матрицу, а картинку рисую сам, и тест с декодером подтверждает, что результат сканируется. Мораль: проверять результат нужно не «картинка создалась», а «её реально можно отсканировать».

### Почему адрес публичный

В QR зашита только короткая ссылка, а она и так открыта любому, кто её знает: никакой секретной информации нет. Зато код можно вставить в обычный `<img>` или печатный макет без токена. Размер ограничен 1024 px, чтобы нельзя было запросить огромную картинку.

### Почему показ QR не считается переходом

Переход — это когда человек реально пришёл на ссылку. Если бы просмотр QR-кода в дашборде увеличивал статистику, владелец сам накручивал бы себе переходы. Поэтому `CheckActive` (в отличие от `Resolve`) не пишет событие в аналитику и не двигает счётчик популярности. Переход фиксируется, когда по QR пройдёт настоящий посетитель.

### Оптимизация: пул буферов

Кодировщик PNG при каждом вызове выделяет около 1 МБ памяти. Я оставил один кодировщик на весь пакет с пулом буферов (`sync.Pool`). Бенчмарк (картинка 256 px): было 1,18 мс и 1 247 111 байт на операцию, стало 0,985 мс и 86 742 байта — памяти в 14 раз меньше.

### Демонстрация с телефоном (по шагам)

1. Ноутбук и телефон подключены к одной сети Wi-Fi.
2. Запустите `Запустить для телефона.bat` из папки программы (при первом запуске Windows спросит про брандмауэр — «Разрешить доступ»).
3. В открывшемся дашборде (`http://<IP ноутбука>/dashboard/`) зарегистрируйтесь и создайте ссылку.
4. Нажмите «QR» в строке ссылки.
5. Наведите камеру телефона на экран и откройте ссылку: страница назначения откроется на телефоне.
6. На ноутбуке нажмите «Статистика»: появился новый переход, в устройствах — мобильный.

Запасной вариант, если Wi-Fi капризничает: показать скриншот `docs/screenshots/07-qr-modal.png`, скачать PNG и отсканировать любым вторым устройством, либо выдать `curl -o qr.png http://localhost/qr/demo.png`.

### Вопросы про QR

**Что такое уровни коррекции ошибок L/M/Q/H?** Это запас избыточности, который позволяет прочитать код, даже если часть его повреждена или закрыта: L — около 7 %, M — около 15 %, Q — около 25 %, H — около 30 %. Чем выше уровень, тем плотнее и мельче модули. Я выбрал M: для короткого адреса это хороший баланс между размером модулей и устойчивостью к потёртостям и бликам.

**Что такое модуль и белая рамка?** Модуль — один чёрный или белый квадратик QR-кода, его «пиксель». Белая рамка (quiet zone) — пустое поле вокруг кода шириной 4 модуля; по стандарту без неё сканер не может отделить код от фона. Поэтому размер картинки получается чуть меньше запрошенного: модуль всегда целое число пикселей, иначе края размоются.

**Почему PNG на 1 бит на пиксель?** В QR всего два цвета, поэтому достаточно палитры из двух цветов: файл в разы меньше, а резкость краёв сохраняется (никаких полутонов, как у JPEG). Стандартный `image/png` это умеет сам, если подать ему палитровое изображение.

**Почему `localhost` не открывается на телефоне?** `localhost` всегда означает «этот же компьютер». На телефоне это сам телефон, а не ноутбук. Поэтому ссылка в QR должна содержать IP ноутбука в локальной сети, а сервис должен слушать не только 127.0.0.1. Это делает `Запустить для телефона.bat`: находит IP физического адаптера Wi-Fi/Ethernet (VPN и виртуальные адаптеры пропускает), запускает сервис на `0.0.0.0:80` с `BASE_URL=http://<IP>`.

**Почему не взять готовую библиотеку целиком?** Взяли: математику кодирования — да. Но отрисовку пришлось написать самим из-за двух найденных багов (см. выше).

## 15. Сохранение данных без базы

### Как это работает (простыми словами)

Раньше в демо-режиме (без PostgreSQL) всё жило только в памяти: закрыл окно — пропали и ссылки, и пользователи, и статистика. К тому же секретный ключ для токенов каждый раз создавался заново, поэтому «слетал» ещё и вход. На показе это неудобно, а ставить целую базу на ноутбук ради демонстрации незачем.

Теперь есть переменная `DATA_FILE` (она задана в запускателях папки «Сократитель ссылок — программа»: `data.json`; в папке для защиты запускатели работают через PostgreSQL, см. раздел 9). Что происходит:

1. При запуске программа читает `data.json` и поднимает из него всё в память.
2. Любое изменение (новая ссылка, переход, регистрация) помечается счётчиком версии. Фоновая горутина видит пометку, ждёт полсекунды (чтобы собрать пачку изменений в одну запись) и записывает файл целиком. Если за это время ничего не менялось, файл не трогает.
3. При нормальной остановке делается ещё одно, итоговое сохранение. Порядок остановки: сначала HTTP-сервер, потом сборщик аналитики дописывает очередь, и только потом сохранение. Поэтому в файл попадают все переходы.
4. Ключ для токенов лежит рядом, в `data.json.secret`. Благодаря этому после перезапуска старый токен ещё действует, и заново входить не нужно.

Рядом с `shortener.exe` появляются два файла. Сброс данных: закрыть программу и удалить оба. Резервная копия: скопировать оба.

### Почему запись «атомарная»

Если просто открыть `data.json` и писать в него, то при выключении питания посреди записи получится обрезанный файл, и все данные пропадут. Поэтому я пишу так: сначала в **временный файл** рядом, сбрасываю его на диск (`Sync`), и потом **переименовываю** поверх старого. Переименование операционная система делает за одно действие: на диске всегда лежит либо целая старая версия, либо целая новая, третьего не бывает.

### Что будет, если закрыть окно крестиком или выключить ноутбук

Закрытие окна убивает процесс без итогового сохранения. Но запись идёт в фоне через полсекунды после каждого изменения, поэтому теряется максимум то, что случилось в последние ~0,5 с. Файл при этом остаётся целым. Я это проверил руками: запустил exe, зарегистрировался, создал ссылку, сделал 5 переходов, убил процесс (`Stop-Process -Force`, это то же самое, что крестик) и запустил снова. Токен принят без входа, вход по паролю работает, в статистике те же 5 переходов.

### Что если файл повреждён

Программа **не запустится** и напишет ошибку, а файл не тронет. Я так сделал специально: если бы она молча начала с пустого хранилища, то первая же фоновая запись затёрла бы повреждённый файл, а в нём ещё можно было что-то спасти. Решение для пользователя: восстановить из копии или удалить файл.

### Вопросы про сохранение данных

**Почему не SQLite?** Это лишняя тяжёлая зависимость. Самый популярный драйвер для Go требует cgo (то есть компилятор C), а чистый вариант заметно увеличивает размер и время сборки. При медленной сети и сборке на ноутбуке это боль. А для продакшена у нас уже есть PostgreSQL. Получается чёткое разделение: **демо** — файл рядом с exe, ничего устанавливать не надо; **продакшен** — PostgreSQL, ради него и сделана вся архитектура.

**Почему не писать на диск при каждом изменении?** Переходов может быть тысячи в секунду, и каждая запись целого файла дорогая. Поэтому пауза в полсекунды (debounce): сколько бы ни было изменений, записей не больше двух в секунду.

**Почему секрет в отдельном файле, а не внутри `data.json`?** Это разные по смыслу данные. Файл данных можно копировать, показывать и сбрасывать, не трогая ключ подписи. Оба файла создаются с правами 0600, чтобы их не читали другие пользователи системы (в данных лежат хэши паролей). Оба в `.gitignore`, в репозиторий не попадут.

**Можно ли указать `DATA_FILE` вместе с PostgreSQL?** Нет, это ошибка конфигурации: было бы два «источника правды» для одних и тех же данных.

**Почему в файле свои структуры, а не модели из `model`?** В моделях поля `PasswordHash` и `VisitorID` скрыты от JSON (`json:"-"`), чтобы случайно не уйти в ответ API. А в файле они нужны, иначе после перезапуска не войти и не посчитать уникальных посетителей. Поэтому для файла отдельные структуры `userRec`, `linkRec`, `clickRec`.

**Это масштабируется?** Нет, и не должно: один процесс, небольшой объём. Это именно демо-режим. Для нагрузки и нескольких экземпляров — PostgreSQL и Redis.
